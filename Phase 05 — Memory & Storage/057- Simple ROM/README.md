# Simple ROM — Circuit + RTL + Testbench Analysis

This design is a **256 × 32-bit synchronous ROM** with an active-low asynchronous reset on the output register and a read-enable control.

```text
ROM depth  = 256 words
Data width = 32 bits
Address    = 8 bits
Capacity   = 256 × 32 = 8192 bits = 1 KB
```

The testbench is **self-checking**: it verifies reset behavior and compares ROM outputs against expected values.

---

## 1. Circuit Overview & Applications

The architecture is:

```text
                 rd_addr[7:0]
                      |
                      v
              +---------------+
              |               |
              |   256 × 32    |
              |      ROM      |
              |               |
              +-------+-------+
                      |
                   32-bit
                      |
                      v
                +-----------+
 clk ---------->| Output FF |----> data_out[31:0]
 rd_en -------->|           |
 rst_n -------->|           |
                +-----------+
```

The ROM contains fixed data generated by:

```systemverilog
rom[i] = 32'h1000_0000 + i;
```

Therefore:

```text
Address 0   → 32'h1000_0000
Address 1   → 32'h1000_0001
Address 2   → 32'h1000_0002
...
Address 255 → 32'h1000_00FF
```

Typical applications include:

* Instruction/data lookup tables
* Constant coefficient storage
* Microcontroller/processor ROM
* FPGA initialization tables
* Control/configuration data
* Lookup-table implementations

---

# 2. ROM Storage

The memory declaration is:

```systemverilog
logic [31:0] rom [0:255];
```

This means:

```text
             8-bit address
                   |
                   v
        +---------------------+
        | 0   → 1000_0000     |
        | 1   → 1000_0001     |
        | 2   → 1000_0002     |
        | ...                 |
        | 254 → 1000_00FE     |
        | 255 → 1000_00FF     |
        +---------------------+
                   |
                32 bits
```

Because there are 256 entries:

```text
2^8 = 256
```

so an 8-bit address is sufficient.

---

# 3. ROM Initialization

The initialization block is:

```systemverilog
initial begin
  for (int i = 0; i < 256; i++) begin
    rom[i] = 32'h1000_0000 + i;
  end
end
```

It fills the complete ROM before normal simulation operation.

For example:

```text
i = 0    → 1000_0000
i = 10   → 1000_000A
i = 100  → 1000_0064
i = 255  → 1000_00FF
```

This is a **simulation/initialization mechanism**. In FPGA implementations, similar initialized ROM structures can generally be inferred into configured memory resources; ASIC implementation would normally use an appropriate ROM structure or macro.

---

# 4. Synchronous Read Logic

The main RTL is:

```systemverilog
always_ff @(posedge clk or negedge rst_n) begin
  if (!rst_n)
    data_out <= 32'h0;
  else if (rd_en)
    data_out <= rom[rd_addr];
end
```

There are three cases.

### Case 1 — Reset active

```text
rst_n = 0
```

causes:

```text
data_out = 0
```

immediately because `rst_n` is in the sensitivity list.

Therefore, the output register has an **asynchronous active-low reset**.

---

### Case 2 — Read enabled

When:

```text
rst_n = 1
rd_en = 1
```

at a rising clock edge:

```text
data_out <= rom[rd_addr]
```

For example:

```text
rd_addr = 8'd20

rom[20] = 1000_0014
```

then after the clock edge:

```text
data_out = 1000_0014
```

---

### Case 3 — Read disabled

When:

```text
rd_en = 0
```

there is no assignment to `data_out`.

Therefore, **the previous output value is retained**.

This is an important difference from your earlier ROM example that explicitly assigned `Z` when reading was disabled.

Here:

```text
rd_en = 0 → data_out holds previous value
```

---

# 5. Synchronous ROM Behavior

The address is not directly connected to the output.

Instead:

```text
rd_addr
   |
   v
ROM lookup
   |
   v
posedge clk
   |
   v
data_out register
```

So changing `rd_addr` alone does not change `data_out`.

The ROM output updates when the clock edge occurs and `rd_en` is asserted.

This makes it a **synchronous-read ROM**.

# 6. Testbench Clock

The TB generates:

```systemverilog
initial clk = 1'b0;
always #5 clk = ~clk;
```

Therefore:

```text
Clock period = 10 ns
Clock frequency = 100 MHz
```

The ROM is consequently being verified at 100 MHz.

# 7. Reset Test

The TB starts with:

```systemverilog
rst_n   = 1'b0;
rd_en   = 1'b0;
rd_addr = 8'h00;
```

Then:

```systemverilog
#12;
```

After 12 ns, it checks:

```systemverilog
if (data_out !== 32'h0)
```

This is a proper self-check.

Expected:

```text
PASS: data_out correctly reset to 0
```

The use of:

```systemverilog
!==
```

is useful in verification because `X`/`Z` values are treated as mismatches.

---

# 8. Address Verification

The TB enables reading:

```systemverilog
rd_en = 1'b1;
```

and tests:

```text
0 → 1 → 2 → 3 → 4 → 5 → 6 → 7
```

For each address:

```systemverilog
rd_addr = i[7:0];
@(posedge clk);
#1;
```

The `#1` gives the DUT's nonblocking assignment time to update `data_out`.

Expected sequence:

```text
Address  Expected
0        1000_0000
1        1000_0001
2        1000_0002
3        1000_0003
4        1000_0004
5        1000_0005
6        1000_0006
7        1000_0007
```

Each value is explicitly checked.

---

# 9. Boundary Test

The TB additionally tests:

```systemverilog
rd_addr = 8'd255;
```

Expected:

```text
32'h1000_0000 + 255
= 32'h1000_00FF
```

This verifies the **maximum valid address**.

So the TB checks both:

```text
Lower range → 0–7
Upper boundary → 255
```

# 11. What the Testbench Does Well

### ✅ Self-checking

It doesn't require you to manually inspect waveforms.

```text
Actual output
     ↓
Expected output
     ↓
Comparison
     ↓
PASS / FAIL
```

### ✅ Reset verification

It explicitly checks the reset value.

### ✅ Directed testing

It verifies known addresses.

### ✅ Boundary testing

It checks address `255`, the maximum possible 8-bit address.

### ✅ Proper synchronous checking

It waits for `posedge clk` before checking the registered ROM output.

### ✅ Clean termination

```systemverilog
$finish;
```

prevents the simulation from running indefinitely.

# 12. One Important Testbench Timing Detail

The TB does:

```systemverilog
rst_n = 1'b1;
rd_en = 1'b1;

for (...) begin
  rd_addr = i[7:0];
  @(posedge clk);
  #1;
  ...
end
```

This is actually a good arrangement because `rd_addr` is assigned **before** waiting for the next rising edge.

So when the ROM reaches:

```systemverilog
@(posedge clk)
```

the correct address is already stable.

For a synchronous ROM, this is the desirable stimulus sequence:

```text
Set address
   ↓
Assert read enable
   ↓
Wait for clock edge
   ↓
ROM captures address/data
   ↓
Wait for NBA update
   ↓
Check output
```

# 14. Limitations / Implementation Considerations

### ROM initialization

The `initial` block is convenient for simulation and FPGA-style initialized memories, but ASIC ROM implementation would normally use a dedicated ROM implementation rather than relying on an RTL `initial` block.

### No explicit behavior when `rd_en=0`

The output holds its previous value because there is no `else` assignment.

That is valid if this behavior is intended.

### Only partial address coverage

The TB checks addresses `0–7` and `255`, not all 256 locations.

Because the ROM is only 256 entries, an **exhaustive 0–255 test** would be easy and would provide stronger verification.

### No error counter

The TB reports individual failures but does not maintain a final total such as:

```text
TOTAL TESTS = 10
PASSED      = 10
FAILED      = 0
```

That would make automated regression testing cleaner.

# 15. Interview Takeaways

### One-line explanation

> **A 256×32 synchronous ROM with an 8-bit address, registered 32-bit output, read enable, and asynchronous active-low output reset.**

### Key questions

**Q: What is the memory capacity?**

```text
256 × 32 = 8192 bits = 1 KB
```

**Q: Why is the address 8 bits?**

```text
2^8 = 256 locations
```

**Q: Is the read asynchronous or synchronous?**

Synchronous, because:

```systemverilog
always_ff @(posedge clk ...)
```

controls the read.

**Q: What happens when `rd_en=0`?**

`data_out` retains its previous value.

**Q: What happens when `rst_n=0`?**

`data_out` is asynchronously cleared to zero.

**Q: Is the ROM itself reset?**

No. The reset only resets `data_out`; it does **not** modify the `rom[]` contents.

**Q: Why is this TB better than a simple `$monitor` TB?**

Because it uses explicit expected-value comparisons and reports **PASS/FAIL**, making it a genuine self-checking verification testbench.
