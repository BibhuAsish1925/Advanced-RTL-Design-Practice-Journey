# 32-BIT DATA WHITENER USING 16-BIT LFSR

## 1. Circuit Overview & Applications

This design implements a **data-whitening block** that XORs input data with a pseudo-random sequence generated by a 16-bit LFSR.

* **Data width:** 32 bits
* **LFSR width:** 16 bits
* **LFSR seed:** `16'hFFFF`
* **Feedback:** `lfsr[15] ^ lfsr[13] ^ lfsr[12] ^ lfsr[10]`
* **Input control:** `valid_i`
* **Output control:** `valid_o`
* **Reset:** Asynchronous active-low
* **Latency:** 1 clock cycle
* **Whitening operation:** `d_o = d_i XOR replicated LFSR pattern`

### Applications

* Communication-system data whitening
* Scramblers
* Reducing long runs of identical bits
* Randomizing structured data patterns
* EMI/pattern-related mitigation
* Digital communication and storage systems

The important distinction is that **whitening does not encrypt the data**. It is intended to make the bit pattern less structured.

---

## 2. Circuit Working & RTL Implementation

### A. LFSR Feedback

The internal LFSR is:

```verilog
reg [LFSR_W-1:0] lfsr;
```

For the configured `LFSR_W=16`, the feedback is:

```verilog
wire fb = lfsr[15] ^ lfsr[13] ^ lfsr[12] ^ lfsr[10];
```

On reset:

```verilog
lfsr <= {LFSR_W{1'b1}};
```

so:

```text
LFSR = FFFF
```

When valid data arrives, the LFSR advances:

```verilog
lfsr <= {lfsr[LFSR_W-2:0], fb};
```

Thus each accepted input word advances the whitening sequence by one LFSR state.

---

### B. Replicating the PN Sequence

A particularly important part of this implementation is:

```verilog
wire [(((W/LFSR_W)+1)*LFSR_W)-1:0] lfsr_rep =
    {(W/LFSR_W)+1{lfsr}};
```

For:

```text
W      = 32
LFSR_W = 16
```

the 16-bit LFSR is replicated twice:

```text
LFSR = ABCD

lfsr_rep = ABCD_ABCD
```

Then:

```verilog
d_o <= d_i ^ lfsr_rep[W-1:0];
```

performs:

```text
32-bit input
       XOR
32-bit replicated PN pattern
       ↓
32-bit whitened output
```

For example, conceptually:

```text
AAAAAAAA
XOR
PN_PN
───────
Whitened data
```

This is more appropriate than XORing the entire input with only a **single replicated bit**, because every data bit is whitened according to the corresponding PN pattern bit.

---

### C. Valid Pipeline

The output valid signal is:

```verilog
valid_o <= valid_i;
```

Therefore the data and valid signal are registered together.

When `valid_i=1`:

```text
d_i ────────────────┐
                    │
                    ▼
                 XOR + LFSR
                    │
                    ▼
                  d_o
                    │
                  valid_o
```

The block processes one valid data word per clock.

When `valid_i=0`, the LFSR does not advance and `d_o` holds its previous value.

## 3. Verification & Testbench

The TB uses a **10 ns clock period**:

```verilog
always #5 clk = ~clk;
```

so:

```text
Clock = 100 MHz
```

After reset, it repeatedly supplies:

```verilog
d_i = 32'hAAAAAAAA;
```

for **8 valid cycles**.

The important test idea is that the **input remains identical**, while the LFSR advances.

Therefore, assuming the LFSR is operating correctly:

```text
Cycle 1: AAAAAAAA XOR PN_1
Cycle 2: AAAAAAAA XOR PN_2
Cycle 3: AAAAAAAA XOR PN_3
...
```

so the output should change even though the input remains constant.

The testbench is primarily **observational**:

```verilog
$monitor(...)
```

It does not calculate an expected whitened value and automatically compare it with `d_o`.

### Stronger verification

A more complete TB could maintain an independent 16-bit reference LFSR and check:

```text
expected_d_o = d_i XOR replicated_reference_lfsr
```

for every `valid_i` cycle.

It could also test:

* `valid_i=0`
* Reset during operation
* Different input patterns
* All-zero data
* All-one data
* Alternating patterns
* LFSR state progression
* Back-to-back valid transactions

## 4. Advantages & Limitations

### Advantages

* Simple XOR-based whitening architecture
* Low hardware complexity
* Parameterized data width
* LFSR advances only when valid data is processed
* Valid and data are registered together
* 16-bit PN sequence is replicated across the 32-bit data path

### Limitations

* The LFSR taps are explicitly verified only for `LFSR_W=16`.
* The parameterization therefore does **not** make arbitrary LFSR widths automatically valid.
* Whitening is **not encryption** and does not provide confidentiality.
* The current TB does not perform automatic data checking.
* LFSR output is deterministic from its seed, so the whitening sequence itself is predictable if the state is known.

### Important RTL point

The comment correctly warns that:

```verilog
lfsr[13]
lfsr[12]
lfsr[10]
```

are only valid indices for the configured 16-bit LFSR. Changing `LFSR_W` below 14 would make those references invalid.

## 5. Interview Takeaways

**One-line explanation:**

> A data whitener XORs input data with a pseudo-random LFSR-generated sequence to reduce predictable or highly structured bit patterns without changing the data width.

### Key distinction

```text
Encryption:
Plaintext → Encryption → Ciphertext
        requires a secret key

Whitening:
Data → XOR with PN sequence → Whitened data
        used for pattern randomization
```

### Important point in this implementation

The LFSR is **16 bits**, but the data path is **32 bits**. Therefore, the LFSR state is replicated:

```text
16-bit PN
   ↓
PN PN
   ↓
32-bit whitening mask
```

This is the key architectural detail that makes the design suitable for the 32-bit datapath.
